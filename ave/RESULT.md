# RESULT.md - итоговые результаты проекта RND на MiniGrid

## 0. Кратко (TL;DR)

Реализован **RND (Random Network Distillation, Burda et al., 2018)** по упрощённой схеме
(одна value-голова PPO, `r = r_ext + β·r_int`, без раздельных GAE) поверх
baseline PPO (Stable-Baselines3) на MiniGrid.

**Главный результат (полный прогон, 200k шагов, seed 42, CPU):**

| Карта | Baseline (ver0) | PPO + RND (ver1, β=0.1) | Роль карты |
| --- | ---: | ---: | --- |
| `MiniGrid-MultiRoom-N2-S4-v0` | 10/10, 95.0 с | 10/10, 129.9 с | Контроль (простая) |
| `MiniGrid-KeyCorridorS3R3-v0` | **0/10**, 384.4 с | **10/10**, 758.3 с | **Целевая: разреженная награда** |
| `MiniGrid-DoorKey-5x5-v0` | 10/10, 124.2 с | 10/10, 197.6 с | Второй контроль |

**Тезис:** на `KeyCorridorS3R3` PPO без novelty **ни разу** не находит цель за весь бюджет
(`0/10`), а PPO + RND решает **10/10**. На картах, где внешней награды достаточно
(`MultiRoom`, `DoorKey`), оба метода дают `10/10`, а RND лишь добавляет время.
Это воспроизводит ключевой тезис статьи: внутренняя награда за новизну критична
**только** при разреженной внешней награде и не вредит (по успеху) там, где награда плотная.

---

## 1. Что именно проверяем

**Что проверяем на упрощённой постановке (MiniGrid):**

1. Помогает ли RND в среде с **разреженной** наградой (`KeyCorridorS3R3`), где baseline не справляется.
2. Не ломает ли RND обучение там, где внешней награды достаточно (`MultiRoom-N2-S4`, `DoorKey-5x5`).
3. Какова **цена** RND по времени на CPU.

**Почему MiniGrid, а не Atari:** Atari (Montezuma’s Revenge и др.) требует миллионов шагов
и часов обучения; MiniGrid даёт те же свойства (разреженная награда, исследование,
процедурная генерация) при бюджете в 200k шагов и секундах-минутах на CPU. Это осознанное
упрощение постановки, оговорённое в разделе «Ограничения».

## 2. Что сделано (и зачем)

### 2.1. Baseline PPO (исходный `train.py`)

- PPO из Stable-Baselines3, `CnnPolicy`, кастомный `MinigridFeaturesExtractor`
  (3 свёртки `kernel=2`, `features_dim=128`), `normalize_images=False`
  (в каналах - индексы объектов, не яркость).
- Логирование по эпизодам: `reward.txt`, `steps_per_ep.txt`, `fps.txt`.
- Ранняя остановка по `reward_delta` за `no_improve_episodes`; сохранение `best_model.zip`.
- **Зачем:** это контрольная точка. Без честного baseline сравнение с RND бессмысленно.

### 2.2. RND-модуль (`src/rnd/`)

- `running_mean_std.py` - `RunningMeanStd` (Welford, `state_dict`/`load_state_dict`):
  нормализация входных наблюдений и внутренней награды. Ранний возврат при `count < 2`
  (фикс шага 1) - устраняет завышенный `r_int` на первых шагах.
- `rnd_module.py` - `RNDModule`:
  - **target** - фиксированная, `requires_grad=False`, random init;
  - **predictor** - обучаемая, Adam(`lr=1e-4`);
  - `_Encoder` устойчив к `H, W ≥ 1` (две свёртки `kernel=3, padding=1` →
    `AdaptiveAvgPool2d(1)` → `Linear(channels, feature_dim)`), работает на 5×5…16×16;
  - автоматическое определение раскладки obs (MiniGrid после `ImgObsWrapper` отдаёт **HWC**
    `(7,7,3)`, а не CHW) и `np.transpose(arr, (2,0,1))`;
  - `obs_rms` (CHW) для входа target/predictor, `reward_rms` для `r_int`,
    `np.clip(normalized, -5, 5)` как защита от выброса.
- `wrapper.py` - `IntrinsicRewardWrapper(gym.Wrapper)`:
  на каждом `step` считает `r_int`, добавляет `β·r_int` к reward, кладёт в `info`
  `r_ext`, `r_int`, `r_int_scaled`, `rnd_loss`, `beta`. Стоит **после** `ImgObsWrapper`.
- **Зачем:** это и есть предмет исследования - novelty-награда. Нормализация obs и r_int
  обязательна, иначе target нестабилен, а β не имеет смысла.

### 2.3. Интеграция в `train.py`

- Добавлены `RND_KEYS`/`RND_DEFAULTS`, валидация, обёртка env при `use_rnd=True`,
  запись `intrinsic_reward.txt` (эпизод, суммарный `r_int`, средний `rnd_loss`, `beta`).
- `best_model` и ранняя остановка - по **внешней** награде `r_ext` (сумма за эпизод),
  а не по `r_ext + β·r_int`: иначе novelty-выброс в первом эпизоде «залипает».
- CLI: `--map/--run-dir/--fixed-params/--device/--seed`.
- **Обратная совместимость:** при `use_rnd=False` поведение идентично исходному `train.py`
  (проверено по кривым).
- **Зачем:** единая точка входа для baseline и RND, чтобы сравнение шло на одном коде.

### 2.4. Пайплайн прогонов и отчёта

- `collect.py` - `ACTIVE_MAPS` (3 карты), `RND_PARAMS`, `main(*, run_rnd, maps)`,
  CLI `--rnd/--all-maps`. Снижены `total_timesteps=200_000`, `no_improve_episodes=500`.
- `report.py` - **не тронут**: таблица времени/успеха и графики `reward`/`steps_per_ep`/`fps`
  работают как раньше; собирает `desktop_verN.md`.
- `summary.json` - сводка по запускам.
- **Зачем:** воспроизводимость. Любой сокомандник одной командой повторяет прогон и отчёт.

### 2.5. Тесты

- `tests/test_rnd.py` - 4 unit-теста, в т.ч. `intrinsic_reward` падает при переобучении
  predictor’а на одном и том же obs (проверка, что novelty действительно «исчерпывается»).
- `pytest tests/test_rnd.py -q` → `4 passed`.
- **Зачем:** без этого теста баг в optimizer/target (например, target обучается) прошёл бы незамеченным.

### 2.6. Полный прогон (финальные артефакты)

- `desktop_ver0.md` - baseline, 3 карты, CPU, 200k шагов, seed 42.
- `desktop_ver1.md` - PPO + RND (β=0.1), те же условия.
- `summary.json`, `desktop_cpu_ver0/`, `desktop_cpu_ver1/` - логи и графики по каждой карте.
- **Зачем:** это данные, на которых стоит весь отчёт.

## 3. Результаты (полный прогон)

Условия: CPU, seed 42, `total_timesteps=200_000`, `max_episode_steps=768`,
остановка «награда не выросла > 0.02 за 500 эпизодов», успех «≥ 7 из последних 10».
CUDA не тестировался (не установлен); по замерам сокомандника узкое место - **среда**,
GPU на MiniGrid выигрыша не даёт.

### 3.1. Таблица время/успех

| Карта | Baseline (ver0): время, цели | RND (ver1, β=0.1): время, цели | Отношение времени |
| --- | ---: | ---: | ---: |
| `MiniGrid-MultiRoom-N2-S4-v0` | 95.0 с, 10/10 | 129.9 с, 10/10 | ×1.37 |
| `MiniGrid-KeyCorridorS3R3-v0` | 384.4 с, **0/10** | 758.3 с, **10/10** | ×1.97 |
| `MiniGrid-DoorKey-5x5-v0` | 124.2 с, 10/10 | 197.6 с, 10/10 | ×1.59 |

### 3.2. Главный результат - `KeyCorridorS3R3`

> PPO без novelty за весь бюджет (200k шагов) **ни разу** не находит цель (`0/10`).
> PPO + RND (β=0.1) решает задачу **10/10**. Задача: 3 комнаты, ключ + дверь + шар,
> внешняя награда разреженная (0/+1). Это прямая иллюстрация тезиса Burda et al. (2018):
> внутренняя награда за новизну критична в средах с разреженной внешней наградой.

### 3.3. Контроль - `MultiRoom-N2-S4`

> Простая карта (2 комнаты, 4×4). Оба метода дают `10/10`. RND не ломает обучение там,
> где внешней награды достаточно; цена - ×1.37 по времени. Это подтверждает, что выигрыш
> RND на `KeyCorridor` - не артефакт, а следствие именно novelty.

### 3.4. Второй контроль - `DoorKey-5x5`

> **Уточнение относительно раннего smoke-прогона (50k):** на полном бюджете (200k)
> baseline **тоже решает** задачу `10/10`, а не `7/100`. Поэтому `DoorKey` - **не**
> «подтверждение, что RND решает, а baseline почти нет», а **второй контроль**:
> оба метода решают, RND добавляет ×1.59 по времени. Это нормально и полезно: у нас
> два контроля (простая и чуть сложнее, но решаемая карта) и одна целевая
> (`KeyCorridor`, где baseline проваливается).

### 3.5. Механизм: `rnd_loss` падает

> За 50k шагов smoke-прогона `rnd_loss` упал примерно с `~0.008` до `~0.000003`
> (~1800–3000×) - predictor учится предсказывать target, novelty «исчерпывается».
> Это ожидаемое поведение RND; в отчёте подкрепляется графиком `r_int`/`rnd_loss`
> по эпизодам (см. п. 5, P1.5).

### 3.6. Цена RND

> RND добавляет **×1.37–1.97** по времени на CPU (среднее ~×1.6). Причина - wrapper +
> forward/backward RND на каждом шаге. На `KeyCorridor` разрыв больше, потому что baseline
> рано останавливается по `no_improve`, а RND учится весь бюджет. GPU-выигрыша не будет:
> узкое место - среда (находка сокомандника), RND только усугубляет разрыв.

## 4. Что получилось, что не очень

### Получилось

- **End-to-end RND-пайплайн** - от wrapper’а до логов; запускается, не падает, учится.
- **Главный тезис воспроизведён на полном бюджете**: `KeyCorridor` `0/10` → `10/10`.
- **Baseline не сломан**: при `use_rnd=False` поведение идентично исходному `train.py`.
- **Раскладка obs HWC** выявлена и починена (была главная причина падений на старте).
- **`best_model` по `r_ext`** - фикс применён, novelty-выброс не доминирует.
- **Фикс шага 1** (`RunningMeanStd.normalize` при `count < 2`) применён; `r_int` на первых
  шагах не завышен; разрыв по времени сократился (было ×1.7 в smoke → ×1.37 на MultiRoom).
- **4 unit-теста** проходят.

### Не очень / технический долг

1. **Один сид (42)** в основном прогоне. Устойчивость результата не подтверждена
   многократно (см. P1.4 в разделе 5).
2. **`intrinsic_reward.txt` не рисуется в `report.py`** - `CHARTS` не расширен.
   График `r_int`/`rnd_loss` делается отдельным скриптом (P1.5) или вручную.
3. **CUDA не тестировался** - в таблице «ошибка». В отчёте: «не тестировался;
   по замерам среда - узкое место, GPU не даёт выигрыша». Это не баг.
4. **Путь "две value-головы, раздельные GAE" не реализован** - осознанное ограничение;
   абляция «две головы vs одна» оставлена как расширение (см. раздел 6).
5. **Абляция β** не сделана - только β=0.1.

## 6. Оговорки для отчёта (готовые формулировки)

1. **Путь B (упрощение):** «RND реализован по упрощённой схеме: одна value-голова PPO,
   `r = r_ext + β·r_int`, без раздельных GAE для extrinsic/intrinsic. Это осознанное
   упрощение относительно Burda et al. (2018); абляция "две головы vs одна" - расширение,
   не реализованное в основном прогоне.»
2. **Нормализация `r_int`:** «`r_int` нормализуется running std и клиппируется в `[−5, 5]`;
   при `count < 2` `normalize` возвращает вход без изменений - это устраняет завышенный
   `r_int` на первых шагах.»
3. **`best_model`:** «`best_model` выбирается по `r_ext` (сумма за эпизод), а не по
   `r_ext + β·r_int` - иначе novelty-выброс в первом эпизоде доминирует.»
4. **CPU vs GPU:** «На MiniGrid узкое место - среда, а не модель; GPU не даёт выигрыша
   (находка сокомандника). CUDA не тестировался; RND добавляет ×1.37–1.97 по времени на CPU,
   потому что добавляет forward/backward RND каждый шаг.»
5. **Предобучение на простой → сложной:** «Не реализуем - уводит от RND (статья явно
   подчёркивает "без демонстраций"); возможное расширение в разделе "обсуждение".»
6. **`DoorKey` - второй контроль:** «На полном бюджете (200k) baseline тоже решает `DoorKey`
   (`10/10`); ранний smoke (50k, `7/100`) не отражал полный прогон. Поэтому `DoorKey` -
   второй контроль, а не подтверждение.»
7. **Один сид:** «Основной прогон - seed 42. Устойчивость проверяется дополнительным
   прогоном на seed 0/1/2 для `KeyCorridor` (P1.4).»
